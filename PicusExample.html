ChainDrop: Inside the Shai-Hulud npm Supply Chain Attack

MURAT CAN ORUNTAK  |  15 MIN READ  |  AUGUST 15, 2026

Key Takeaways

  • ChainDrop is the August 4, 2026 wave of the Shai-Hulud npm worm, a self-propagating, credential-stealing supply chain attack.
  • The malware executes through an npm preinstall hook, running a heavily obfuscated Bun-based payload before installation completes.
  • It steals npm, GitHub, cloud, and CI/CD credentials, then reuses any npm token with write access and 2FA bypass to poison and republish further packages without operator involvement.
  • Microsoft Threat Intelligence and Elastic Security Labs each reported more than 400 affected npm packages, and vendor estimates of the combined exposure range from 1.3 to over 2 billion monthly downloads. All counts were taken while the campaign was still spreading, so the real figures may be higher.
  • The Picus Security Validation Platform lets teams validate controls against supply-chain attack techniques like those used by ChainDrop, see whether prevention and detection actually fire, and close the gaps with ready-to-use mitigation content.

Modern applications depend largely on open-source libraries, often hundreds of them, and many arrive indirectly, as dependencies of dependencies. This is largely what makes supply chain attacks against open-source registries so dangerous: a single compromised package can spread far beyond its own users through routine installs and updates. ChainDrop, the August 2026 wave of the Shai-Hulud npm worm, shows what happens when that compromised package can also propagate on its own.

What Is ChainDrop?

ChainDrop is a self-propagating, credential-stealing npm worm first reported on August 4, 2026. It entered the ecosystem through the compromised maintainer account behind the keyv and cacheable caching libraries, executes automatically via an npm preinstall hook, and steals npm, GitHub, cloud, and CI/CD credentials from developer machines and build runners. Any stolen npm token with publish rights is then reused to poison and republish further packages, which is how a single account takeover grew into hundreds of compromised packages within hours.

Shai-Hulud Lineage

Shai-Hulud first appeared in September 2025, poisoning more than 500 npm packages including the widely used @ctrl/tinycolor. A second wave called "The Second Coming" followed in late 2025, introducing a Bun-based preinstall payload, and a variant called Mini Shai-Hulud abused GitHub's trusted publishing workflows in April 2026. [1] Picus previously analyzed both the original Shai-Hulud worm and the Mini Shai-Hulud variant in depth. ChainDrop, first reported on August 4, 2026, is the latest wave in this lineage. [2]

Before going further, one point shapes how the rest of this should be read: lineage does not always mean attribution. There are multiple indicators tying ChainDrop to the documented Shai-Hulud toolchain: the PBKDF2-based string decoder, the Bun 1.3.13 pin, the check that aborts execution on Russian-language systems, the self-applied "Shai-Hulud: Here We Go Again" marker, the Dune-derived naming carried through to the victim-owned exfiltration repositories, the IDE and AI-tool persistence planted in .vscode and .claude configuration paths, and the overall npm-propagation plus GitHub-exfiltration architecture. Together these point toward the same operator. However, since the Shai-Hulud source was published in May 2026 and is available to anyone, the campaign cannot be certainly attributed to the TeamPCP group. So the code lineage is clear, but the operator is not.

What sets ChainDrop apart from earlier waves is its command-and-control addressing: instead of a hardcoded domain, the active endpoint is resolved from an Ethereum smart contract, with a signed commit-search fallback behind it, so the operator can move the destination with a single on-chain transaction rather than shipping a new build. It is examined in detail later in this analysis. [3]

How ChainDrop Works

The attack targeted keyv, a small but foundational library that gives Node.js developers a unified key-value storage interface, so they can add caching without writing backend-specific code. It sits deep in the dependency tree of countless projects, and so do its sibling caching libraries. That reach is what turned a single account compromise into an ecosystem event within hours. In the preceding month, keyv alone saw over 600 million downloads. [4] Almost none of those installs were deliberate choices by a developer; they were transitive pulls underneath something else. [5]

ChainDrop spread in two distinct stages, and telling them apart is the key to understanding the attack. Everything that happens after a poisoned package lands on npm is the same in both cases.

Stage one: break-in (T1195.002, Compromise Software Supply Chain). The attacker took over the account of the maintainer behind keyv and its sibling libraries, pushed malicious code into the shared repository holding all of them, and cut new releases. [4] How that account was reached is still unclear; the evidence points to stolen maintainer credentials, but no report names the credential type or the method. [6]

Stage two: worm. The npm tokens found in the collected data (harvested in the credential-theft phase described below) are checked for package-write permission and 2FA-bypass capability. Tokens failing either check are skipped. [4]

For each package the token can reach, the routine pulls down the latest tarball, drops the current malware bundle inside it, adds a loader, and rewrites the lifecycle scripts. That is the core observed propagation mechanism: a single stolen token turns into a malicious patch release on every package its owner can publish to. It also explains the shape these releases took on npm, showing up as routine patch bumps with no source commit or pull request behind them. [6]

What runs when lifecycle scripts execute

The only change to package.json is a single preinstall lifecycle script (T1059.007, Command and Scripting Interpreter: JavaScript). npm runs it before installation completes, so the payload executes on a developer workstation or CI/CD runner before the install finishes and before many post-install validation steps can occur. The script launches setup.mjs, a small cross-platform dropper that works on Linux, macOS, and Windows. If the Bun runtime (a legitimate JavaScript runtime, not compromised here, just borrowed as a portable execution vehicle that draws less attention where detection is tuned for Node.js [3]) is not already on the system, the dropper detects the host platform and architecture and downloads Bun 1.3.13 from its legitimate release page, then uses it to execute the obfuscated payload. Once execution completes, the temporary Bun directory is deleted (T1070.004, Indicator Removal: File Deletion), a small anti-forensic touch that removes the most obvious artifact from disk. [4]

The payload itself ships under two different filenames, and the difference is diagnostically useful. Packages compromised directly from the keyv monorepo carry Math_Symbol.js, while packages trojanized later by worm propagation carry math_init.js. Both files share the same SHA-256 hash. The filename therefore acts as a marker of infection generation: it tells a responder whether a given package was part of the original compromise or a downstream casualty, without changing what the code does. [4]

Before it does anything else, ChainDrop looks at where it has landed:

  • If the system language is Russian, it quits on the spot (T1614.001, System Language Discovery).
  • If a copy is already running, the new one stops, which prevents concurrent duplicate execution.
  • If no CI environment is detected, it assumes it is on a developer machine and relaunches itself as a detached background process, so it outlives npm install and keeps running after the install finishes.
  • If a CI environment is detected, it stays attached to the active job instead. Detaching offers little here, since execution is already bound to the job's lifetime, and remaining attached is enough for it to read the secrets, runner credentials, and OIDC tokens available to that job.

Credential theft

Once these environment checks pass, the malware turns to its real objective: hunting for credentials. It reads environment variables, shell histories (T1552.003, Unsecured Credentials: Bash History), cloud configuration files (T1552.001, Credentials In Files), and SSH keys (T1552.004, Private Keys), and pulls tokens from developer tools like the GitHub CLI (T1528, Steal Application Access Token), Docker, Terraform, and Vault. It also reads the config and auth files of AI coding tools, which often hold API keys billed to the organization. [3]

On Linux GitHub Actions runners it goes one step further and reads the runner process memory directly (/proc/<pid>/mem, T1003.007), catching short-lived OIDC tokens and secrets that never touch disk at all. [5]

The payload then authenticates to npm, GitHub, AWS, Kubernetes and Vault with the collected credentials, calls each provider's API to list the resources that identity can reach (T1526, Cloud Service Discovery), and pulls the further secrets it finds there.

Exfiltration and C2

Collected data is serialized, gzip-compressed, and encrypted with an AES-256-GCM key, then wrapped with the attacker's RSA public key (T1573.002, Encrypted Channel: Asymmetric Cryptography). Exfiltration goes to an attacker-controlled HTTPS endpoint, but the domain is not hardcoded. It is resolved at runtime (T1568, Dynamic Resolution) from an Ethereum smart contract at 0xE1f2395ee43e45A1556EC6438a88c31B83493103, so the operator can rotate infrastructure with a single blockchain transaction without touching the deployed malware. This happened on August 4, when the active domain was swapped on-chain. [3] The domains seen in use were awqhnjewqjkl[.]icu and npm-cache[.]com. [4]

For C2 resolution the contract lookup is the primary mechanism, attempted against roughly 60 public Ethereum RPC endpoints until one answers, so blocking a single provider does not stop it. A signed GitHub commit acts as the fallback: the worm searches commit history for a marker (thebeautifulmarchoftime) and accepts a recovered domain only after checking it against an RSA public key embedded in the payload, so a defender cannot plant a fake marker and sinkhole the worm. That fallback was not in use at the time of analysis, since no valid operator record existed. [3]

The main payload exfiltrates harvested host data over two channels: the HTTPS endpoint above, and victim-owned GitHub repositories. Different vendors disagree on which is the primary channel and which is the fallback. [8] For the GitHub channel, the worm creates a public repository under the victim's own account, described as "Shai-Hulud: Here We Go Again", and commits the encrypted results there as results-<timestamp>-<counter>.json files (T1567.001, Exfiltration to Code Repository). That is how 453 candidate victim repositories were found. [3]

Separately, ChainDrop can exfiltrate repository secrets through a malicious GitHub Actions workflow. It plants a .github/workflows/codeql_analysis.yml file that serializes ${{ toJSON(secrets) }} and uploads the result as an ordinary Actions artifact. [3] Blocking the network route therefore does not close the problem, because the repository and artifact paths blend into ordinary authenticated GitHub traffic and evade simple domain-based blocking. Blocking a C2 domain with an HTTP error page also backfires, since the worm treats 400 and 404 responses as a healthy server. A sinkhole is therefore preferable to simple HTTP-error blocking.

After sending data, the payload reads the server's HTTP response, parses it as JSON, and evaluates a code field if one is present. [3] No second stage is baked in, so the operator can serve different follow-on code to each victim at request time. A correctly formatted synthetic request to the live endpoint returned an empty response, so this channel was disarmed, selectively gated, or asynchronous at test time. It exists in the code, but was not confirmed firing.

Persistence

ChainDrop also establishes persistence in developer tooling. Using stolen GitHub credentials, it injects the malware and its loaders into eligible repository branches, targeting Claude Code and VS Code configuration paths: .claude/settings.json, .claude/setup.mjs, .vscode/tasks.json and .vscode/setup.mjs. [6] The VS Code task is labeled Environment Setup and fires on folderOpen; the Claude hook fires on SessionStart (T1546, Event Triggered Execution). This creates a secondary infection route: opening the folder or starting a session can restart the payload long after the npm install finished.

In order to remove this persistence mechanism, all five files across both directories have to be deleted. [3] Also, with a GitHub App token in hand the worm wrote the same files into up to 50 branches per repository, so every branch needs checking. [4]

ChainDrop also carries a second, OS-level persistence mechanism aimed at keeping a credential monitor running on the host. It installs a macOS LaunchAgent (com.user.gh-token-monitor) and a Linux systemd user service (gh-token-monitor.service), which keep watching for GitHub tokens and re-run the payload independently of the editor hooks above. Because these live at the operating-system level rather than inside the project, responders should hunt for both artifacts directly. [3]

Evasion Mechanisms

ChainDrop was not invisible. Behavioral detections could identify several of its actions, and security vendors found the campaign quickly. However, since the attack mainly ran through tools, workflows and network services that developers already use every day, the malicious behavior blended into otherwise legitimate software-development activity, which is what let it spread through hundreds of packages before the pattern stood out. On top of that blending, it leaned on several techniques to slow the analysts who did look: the payload was heavily obfuscated, its network destinations were built to change, and no single action looked malicious on its own.

Obfuscation

The payload was heavily obfuscated, making static inspection and signature creation more difficult. Analysts first had to decode strings and unwrap multiple transformation layers before the program's logic became readable [3].

Obfuscation did not remove the malware's observable behavior. The payload still had to execute processes, read credentials, access runner memory and communicate externally. Its value to the attacker was mainly to delay understanding and make static detection more difficult while the campaign was spreading.

Network indicators

The blockchain-based C2 resolution and layered payload encryption described above have a shared operational consequence worth stating plainly: the operator can move the destination with a single on-chain transaction, and even if a defender inspects the TLS connection, the data inside is still encrypted, because ChainDrop encrypts it with AES before it ever enters the tunnel. Together, these choices reduced the value of static domain blocklists and simple network-content inspection while the campaign was live.

Detection depended on relationships, not individual indicators

ChainDrop's defensive advantage was not that its actions were impossible to detect. It was that many individual components were legitimate:

  • npm was legitimate.
  • Bun was legitimate.
  • GitHub and cloud APIs were legitimate.
  • The CI workflow could be legitimate.
  • A provenance signature could be valid.
  • HTTPS traffic could look routine.

The signal was never in any one component but in the relationships between them: an install hook launching an unexpected dropper, Node handing execution to Bun, Bun reaching for credential helpers, or a CI runner having its process memory read. ChainDrop even carried a fully implemented path to abuse OIDC trusted publishing and produce a malicious package with valid provenance, though it was not seen executing. [3] For defenders, that shifts detection away from any single file, signature or domain and toward validating the full execution and release chain.

How to Detect and Prevent ChainDrop

Response has two halves: finding out whether you were exposed, and cleaning up without triggering the malware's own defenses.

Detection: what to look for

  • Preinstall hooks and payload files. Audit package.json files and lockfiles for unexpected preinstall entries referencing setup.mjs. For payload files, hunt Math_*.js and math_<guid>.js as a wildcard rather than the two known names alone. [6]
  • Rogue GitHub repositories. Search your organization for unexpected public repositories described as "Shai-Hulud: Here We Go Again", paired with Dune-derived names such as sardaukar or harkonnen. Private repositories will not appear in such a search, so a clean result is not proof. [3]
  • Worm-authored commits. Propagation commits carry a consistent signature: author claude (claude@users.noreply.github.com) with the message chore: update config. Searching organization history for that pair is a high-signal, low-effort check. [4]
  • The commit-message credential channel. Search commit history for the marker IfYouBlockThisAPIKeyItWillCrashTheLiveProductionServersOfAllThirdPartyClients. A stolen token sits behind it, double-Base64 encoded and nothing more. A hit means a live credential is in a public commit; revoke it. [6]
  • Editor and workflow config tampering. Check for unauthorized .claude/settings.json or .vscode/ entries, and for an unexpected .github/workflows/codeql_analysis.yml containing toJSON(secrets). Check every branch, not just the default one. [3]
  • Bun staging directory. The dropper deletes its temporary bun-dl- directory afterwards, but process telemetry retains the path, which makes it a useful hunting anchor. [6]
  • CI build logs. Review logs and lockfiles for known-bad versions of keyv, cacheable, flat-cache and related packages. [7] In CI the worm runs inline rather than detaching, so its debug output lands in the workflow log. [3]

The best place to catch this is the moment one process starts another: Node starting the dropper, then Bun running a payload filename that would be unexpected in a legitimate project context.

Microsoft publishes a similar query for Defender XDR. It catches the campaign's most telling move in one line: a Bun process calling command-line tools to grab credentials and access tokens.

Cleanup

To clean up, clear the npm and yarn caches on affected machines and build hosts, lock each project to a known-safe version so it stops pulling the bad one, and rebuild any shared base images and build runners that picked it up. [6] Then change any credentials that may have leaked, after making sure every persistence mechanism has been removed from the machine. One thing to watch: if a machine still has the payload's token monitor on it (files like ~/Library/LaunchAgents/com.user.gh-token-monitor.plist or ~/.config/systemd/user/gh-token-monitor.service), delete it before you revoke the token, because it can do damage when it sees the token being revoked. [3] For prevention going forward, one of the most effective steps is upgrading to npm 12 or later, which blocks install-time lifecycle scripts like preinstall by default and removes the exact mechanism the campaign relies on to run. [4]
